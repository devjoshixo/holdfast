why row-per-seat: it is the only schema where all three mechanisms — each a different approach to the same problem — can coexist and be compared fairly. a single row with a seat counter would shut one of them out: the unique-constraint check could never even enter the picture, because a unique constraint polices row existence (no two rows with the same seat), not a number counting down inside one row. so to run a real three-way shootout, every mechanism needs the row-per-seat arena.

metrics (the shootout is judged on these, not just correctness — all three are correct, the question is which is best under load):

1. throughput (successful bookings per second) — exposes wasted work. all three produce only one winner, so that is not the difference; the difference is what the losers cost. with the unique constraint, every loser still runs a full insert that the database processes and then rejects (23505) — real work burned for zero bookings. cas is the same plus retries (updates that match zero rows, then loop). that wasted work steals database capacity from other seats' bookings, so throughput drops for constraint and cas.

2. p99 latency (the slow tail — the time the unluckiest 1% of requests wait) — exposes the row lock. the lock queues losers, so if one booking at the front is slow (twice the average or worse), everyone behind it in the queue waits too. one slow request blocks the whole line (head-of-line blocking), and that inflates the tail. the constraint and cas fail fast instead of queuing, so their tail stays flat.

3. retry rate (how often a client has to resend the request) — exposes cas. retrying is the heart of cas: a loser matches zero rows, re-reads, and tries again. the unique constraint gives a clear final answer ("seat taken") so there is no retry loop; the lock waits then answers definitively. only cas drives the retry rate up.
