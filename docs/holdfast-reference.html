Holdfast · Correctness under contention

Holdfast Field Manual

A complete reference to the booking engine: the contract it holds, the three mechanisms measured against each other, the harness that had to be fixed three times before it told the truth, and the exact state of the work in progress.

Go · PostgreSQL 16 · pgx v5 M0–M2 complete · M4 in progress Reference built 2026-09-22

01What it is, and the one claim

Holdfast is a seat-booking engine. Booking seats is not the point. The point is a single property, held under conditions that break the naive version of this code everywhere it is written.

Concurrent requests can never double-sell the same seat, and never lie about the outcome — no overselling, no false “sold out,” and a retried request always resolves to exactly one booking.

Every claim in that sentence is backed by a test that would fail if the claim were false. That is the distinction the whole project turns on: the guarantee is measured, not asserted.

The problem is not invented. The naive check availability, then book pattern — with no unique constraint and no lock or transaction around the insert — is a live race condition found in production code at work. Holdfast is the version that is actually correct, with the test that proves it.

The layered structure, on purpose

The milestones are not features. Each one introduces a different reason the system could be wrong, even when every earlier reason has been handled:

02The correctness contract

Written in plain English before any code existed. Four guarantees, verbatim from docs/M0-contract.md. Everything downstream is an attempt to keep them.

Guarantee 1 — no oversell, no undersell

No matter how many requests come in — be it 5,000 — only 100 tickets are booked. Nothing is undersold, nothing is oversold. Exactly N. Not >, not <.

Guarantee 2 — no false rejection

The system will not return a “no tickets” error while tickets remain. If the ticket is available at the time of the write, the booking is done.

Guarantee 3 — no imaginary reads

A read is never a made-up number — always a snapshot of the real tickets sold and left at that moment.

Guarantee 4 — retries are retries

If a booking commits but the response is lost before the client sees it, and the client sends the same request again, the system treats it as a retry, not a new request: no second booking is created, and the retry receives the outcome of the original attempt — whatever that outcome was.

Why Guarantee 1 is two-sided

Most implementations only defend against overselling. Underselling is equally a bug and much harder to notice: a user who is told “sold out” while a seat sits free never files a report, they just leave. The contract names both because only naming both forces a test that can catch both.

The trap inside “exactly N”

A totals check can pass while the system is broken. With 100 seats you can observe exactly 100 bookings where seat 14 was sold twice and seat 15 was never sold. Totals net out; correctness does not. This is why the harness asks the database directly — GROUP BY seat_id HAVING count(*) > 1 — instead of trusting a count.

03Data model and schema

Row-per-seat, and why that choice came first

A seat is a row. The alternative — one row per event carrying a seats_remaining counter — was rejected for a reason specific to this project:

Row-per-seat is the only schema in which all three mechanisms can coexist and be compared fairly. A unique constraint polices row existence, not a number counting down inside one row — a counter schema would have silently excluded one of the three contestants from the shootout.

That is a benchmark-design decision made before any benchmarking, and it is the kind of thing worth being able to say out loud: the arena was chosen so that the contest was fair.

Read that CHECK constraint again

held_requires_holder makes an illegal state unrepresentable in the database. A seat can never be held by nobody, or held with no deadline — not because application code is careful, but because Postgres will refuse the row. Application care is a habit; a constraint is a guarantee. This is the same move as the UNIQUE on request_id: push the invariant down to where it cannot be forgotten.

The seat state machine

free→ held→ booked
held— held_until < now() → free (implicitly)

The expiry transition is the subtle one, and the design choice inside it matters: expiry is not an event, it is a predicate. No background job flips a seat back to free. A seat whose held_until has passed is treated as available by the WHERE clause of the next request that wants it:

WHERE id = $2 AND (status='free' OR (status='held' AND held_until < now()))
Why the database owns the clock

The authoritative expiry decision lives in a database timestamp compared against the database's now(), not in an application timer. Only one of those survives a pod death. An in-process time.AfterFunc holding a seat's release is a guarantee that evaporates when the process does — and it also disagrees with every other replica's clock in M5. Make the database the single clock and the reaper becomes an optimisation, not a correctness requirement.

There is also a SeatStatus enum — free, booked, held — used everywhere instead of string literals. The comment in the source states the reason plainly: a typo in a hand-typed "free" inside a compare-and-swap predicate does not throw. It silently never matches, and the mechanism quietly stops working while every test that checks for overselling still passes.

05Three mechanisms

Three ways to make a seat claim atomic in Postgres, all three correct, implemented behind one signature so the same harness can attack any of them:

type bookFunc func(ctx context.Context, pool *pgxpool.Pool,
    eventID, seatID int64, customer, requestID string) (Outcome, int, error)

The middle return value is the retry count — it exists because only one of the three mechanisms can produce retries, and the harness needs to see that difference.

1 · Pessimistic row lock

  1. BEGIN
  2. SELECT … FOR UPDATE on the seat row
  3. Check bookings under the lock
  4. Free → INSERT; taken → seat_taken
  5. COMMIT releases
Loser pays: time queued behind the row.

2 · Unique constraint

  1. Look up request_id in bookings
  2. Found → already_mine
  3. Else fire the INSERT
  4. 23505 → seat_taken
Loser pays: a full INSERT that Postgres rejects.

3 · Compare-and-swap

  1. Claim request_id first
  2. Read seats.status
  3. UPDATE … WHERE status='free'
  4. 0 rows → re-read, loop
  5. INSERT booking, record outcome, commit
Loser pays: one cheap read, then exits.

All three produce exactly one winner. They are identical in correctness and completely different in what a loser costs — and since almost every request in a flash sale is a loser, the cost of losing is the performance of the system.

Mechanism 1 — the row lock, in full

tx, err := pool.Begin(ctx)
defer tx.Rollback(ctx) // safety net; harmless no-op after a successful Commit

// lock the seat row — just the lock, nothing else
err = tx.QueryRow(ctx, "SELECT id from seats WHERE id = $1 FOR UPDATE", seatID).Scan(&lockedSeat)

// under the lock, ask whether it is already booked
err = tx.QueryRow(ctx, "SELECT id from bookings WHERE seat_id = $1", seatID).Scan(&existingBooking)
if err == nil { return OutcomeSeatTaken, 0, nil }
if !errors.Is(err, pgx.ErrNoRows) { return OutcomeSystemError, 0, err }

_, err = tx.Exec(ctx, "INSERT INTO bookings (...) VALUES ($1,$2,$3,$4)", ...)
err = tx.Commit(ctx) // releases the lock

What makes it correct: FOR UPDATE takes an exclusive lock on the seat row. A second transaction reaching the same line blocks until the first commits or rolls back. By the time it reads bookings, the winner's row is visible. The check-then-act gap is closed by serialising the two competitors, so there is no gap to race in.

The property that hurts it: losers queue. One slow holder at the front of the line delays everyone behind it — head-of-line blocking. Fewer seats means more requests behind the same row, so the cost grows precisely as contention rises.

defer tx.Rollback(ctx) before any early return is the idiom that makes the nine possible exit paths safe. Rollback after a successful commit is a no-op, so one deferred line covers every failure exit without a single explicit rollback call.

Mechanism 2 — the unique constraint, in full

err := pool.QueryRow(ctx, "SELECT seat_id FROM bookings WHERE request_id = $1", requestID).Scan(&foundSeat)
if err == nil { return OutcomeAlreadyMine, 0, nil }
if !errors.Is(err, pgx.ErrNoRows) { return OutcomeSystemError, 0, err }

_, err = pool.Exec(ctx, "INSERT INTO bookings (...) VALUES ($1,$2,$3,$4)", ...)
if err != nil {
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) && pgErr.Code == "23505" {
        return OutcomeSeatTaken, 0, nil   // the constraint did the work
    }
    return OutcomeSystemError, 0, err
}
return OutcomeBooked, 0, nil

What makes it correct: UNIQUE (event_id, seat_id) on bookings. Two concurrent inserts for one seat cannot both land; the storage engine serialises on the index entry and rejects the second with SQLSTATE 23505 (unique_violation). Note it needs no explicit transaction at all — a single statement is its own transaction, and the constraint is the whole mechanism.

The property that hurts it: the loser's exit is not cheap. It fires a real INSERT, Postgres parses it, plans it, attempts the index write, detects the collision, and rolls it back. That is real work burned for zero bookings, and it happens on nearly every request.

Idiom worth memorising

errors.As(err, &pgErr) && pgErr.Code == "23505" is how you distinguish “this failed because someone beat me” from “this failed because the database is broken.” Treating both the same way is how a race condition gets reported as an outage — and how a genuine outage gets reported as a lost race.

Mechanism 3 — compare-and-swap, in full

The one that carries the most design. It is also the one M2 built on, so read it alongside §10.

tx, _ := pool.Begin(ctx)
defer tx.Rollback(ctx)

// --- the claim (M2) — a SAVEPOINT, so a 23505 here does not poison the outer tx
txc, _ := tx.Begin(ctx)
_, err = txc.Exec(ctx, "INSERT INTO request_lookup (request_id,seat_id) VALUES ($1,$2)", requestID, seatID)
if err != nil {
    if pgErr.Code == "23505" {
        txc.Rollback(ctx)                       // roll back ONLY the savepoint
        // read the original decision back and return it
        tx.QueryRow(ctx, "SELECT outcome,seat_id FROM request_lookup WHERE request_id = $1", requestID).
            Scan(&outcome, &storedSeatID)
        if seatID != storedSeatID { return OutcomeClientSideError, retries, nil }
        if outcome == string(OutcomeBooked) { return OutcomeAlreadyMine, retries, nil }
        return Outcome(outcome), retries, nil
    }
    return OutcomeSystemError, retries, err
}
txc.Commit(ctx)                                  // release the savepoint

// --- the CAS loop
for {
    tx.QueryRow(ctx, "SELECT status from seats WHERE id = $1", seatID).Scan(&freeSeat)
    if freeSeat == string(SeatStatusBooked) {
        tx.Exec(ctx, "UPDATE request_lookup SET outcome = $1 WHERE request_id = $2", OutcomeSeatTaken, requestID)
        tx.Commit(ctx)
        return OutcomeSeatTaken, retries, nil
    }
    newSeat, _ := tx.Exec(ctx,
        "UPDATE seats SET status = $1 WHERE id = $2 AND status = $3",
        SeatStatusBooked, seatID, SeatStatusFree)
    if newSeat.RowsAffected() > 0 { break }      // we won
    retries++
}

tx.Exec(ctx, "INSERT INTO bookings (...) VALUES ($1,$2,$3,$4)", ...)
tx.Exec(ctx, "UPDATE request_lookup SET outcome = $1 WHERE request_id = $2", OutcomeBooked, requestID)
tx.Commit(ctx)
return OutcomeBooked, retries, nil

The three things to understand in that code

1. RowsAffected() is the compare-and-swap. The UPDATE carries its own precondition in the WHERE clause: change this row to booked, but only if it is still free. Postgres evaluates the predicate and performs the write as one atomic operation — there is no window between checking and acting, because they are the same statement. If someone else got there first, the predicate fails, zero rows change, and RowsAffected() returns 0. That return value is the answer to “did I win?”

2. The nested tx.Begin is a savepoint, not a second transaction. In pgx, calling Begin on an existing transaction issues SAVEPOINT. This matters enormously: in Postgres, any error inside a transaction poisons it — every subsequent statement fails with current transaction is aborted until you roll back. The 23505 from the claim insert is an expected event, not a failure, so it must not destroy the transaction that still has to read the stored outcome. The savepoint scopes the damage: roll back to the savepoint and the outer transaction is healthy again.

3. The loop exists because CAS can lose without being wrong. Zero rows affected does not mean “taken” — it means “state changed under me.” The seat could have been booked, or it could have gone free → held → free while this request was reading. So the loop re-reads, decides, and either exits with an answer or tries again. That loop is the retry rate the benchmark measures.

06The harness that tried to lie

The mechanisms are short. The harness is the real work, and it is where most of the two weeks went.

The arena

TRUNCATE bookings, seats, events, request_lookup RESTART IDENTITY CASCADE
INSERT INTO events (name, total_seats) VALUES ('racefest', $1)
-- then N seats, labelled seat-0 … seat-(N-1)

Every run starts from a clean arena. RESTART IDENTITY resets the sequences so ids are comparable across runs; CASCADE handles the foreign keys.

Two Go details that are load-bearing

results[i] needs no mutex. Each goroutine writes exactly one slot it alone owns. Distinct elements of a slice are distinct memory; there is no shared write. Adding a lock here would not make it safer, it would make the benchmark measure the lock.

close(start) is the starting gun. Closing a channel unblocks every receiver simultaneously. Sending 10,000 values would release them one at a time — which is exactly one of the three ways this harness lied (below).

The four assertions

CheckAsksCatches
1Bookings within [rangeLow, seatCount]Gross over- or under-selling
2system_error == 0Crashes dressed up as losses
3aDB row count == clients told bookedThe system lying to a user
3bGROUP BY seat_id HAVING count(*) > 1A double-sold seat masked by an unsold one
retryRe-run every request with the same request_idGuarantee 4 violations

Check 3a is the reconciliation that most test suites never write: it compares what the clients were told against what the database holds. A system can be internally consistent and still lie to users; only comparing the two surfaces catches it.

Check 3b exists because of the trap in Guarantee 1 — totals can net out. Asking the database for duplicate seat ids is the only check that cannot be fooled by compensating errors.

The three times the harness lied

This is the most transferable part of the entire milestone, and the part worth leading with when someone asks what was hard. Each of these produced numbers that looked completely reasonable and meant nothing.

Lie 1 — overlapping batches

Batches were not fully draining before the next started, so contention from one run bled into the next. Fix: the 6-second gap between releases.

Lie 2 — serialised release

Goroutines were being released one at a time rather than together, so nothing actually raced. The benchmark was measuring sequential throughput and calling it contention. Fix: close(start).

Lie 3 — the contest ended before it began

With a single seat, the whole contest resolved in about five milliseconds — long before enough competitors had arrived to contend at all. Fix: setupArena was changed to create many seats, and the pool became the independent variable.

Knowing which mechanism is faster matters far less than knowing whether your measurement is telling you the truth.

What the shape means

There is no single best mechanism. The row lock wins when demand is spread out; compare-and-swap wins when it concentrates on a few hot seats; the unique constraint never wins.

Two claims live in that table and they land on different mechanisms — worth keeping separate, because conflating them is the easiest way to misreport the result:

  • “Slowest at every level” is the unique constraint. It is the highest number in all four rows.
  • “The only one that degrades under contention” is the row lock: 2.63 → 3.77. The constraint actually improves, 6.32 → 4.19.

The explanation is the cost of losing. The row lock's losers queue on the same row, and the queue grows as seats become scarce. The constraint's losers each fire a rejected write regardless. CAS's losers read once and leave — and as contention rises, more of them take that cheap path earlier.

Reproduced across independent runs. Max request time and p99 were close together, so the requests were fairly evenly timed rather than dominated by a few outliers.

08The hypothesis the data killed

The first written explanation was: the constraint slows down because more inserts fail as seats get scarce. It is intuitive, it fits the mechanism, and it is wrong. The project's own numbers contradict it.

Seat poolFailed insertsCommitted insertsConstraint p99
10,000~20,00010,0006.32 s
10~29,990104.19 s

Failures go up while latency goes down. Failed writes therefore cannot be what drives it. What moves in the same direction as the latency is the number of committed inserts: 10,000 versus 10.

The likely mechanism: a committed insert leaves a heap row, an entry in the unique index, and a WAL record that must be flushed to disk before COMMIT returns. A rejected insert is turned away at the index and leaves none of the three. Fewer seats means fewer commits means less durable work.

The honest epistemics, kept deliberately

This has not been profiled. It is the likely explanation, not a measured one. What is established is the negative: the failed-write story is ruled out by the data. Separating “I proved X is false” from “I suspect Y is true” is the whole difference between a measurement and an opinion — and stating that boundary out loud is worth more in an interview than a confident guess.

What the benchmark does not measure

  • Not an isolated contention test. Database latency, connection-pool queueing and system noise are all inside these numbers. It is an honest end-to-end request benchmark, not a clean measurement of contention alone.
  • All local. Postgres ran in a Docker container on the same machine. A network between the client and the database adds latency and dropped requests that would shift every number.
  • One skew only. The 80/20 split was fixed across all runs. At 50/50 the row lock might well take the lead back from CAS — that was never tested, so it is not claimed.
  • Connection-pool queueing is included. 30,000 requests through 90 connections means roughly 111 requests queueing per connection. Every mechanism faces the same pool, so the comparison stays fair, but the absolute numbers carry that delay.

The M0 bet: overturned

M0 picked the row lock. The measurement said otherwise: CAS won across the tested cases, and the row lock degraded exactly where the flash-sale premise lives — at the concentrated end. The bet was overturned by the project's own data, which is the entire reason for running the shootout instead of reading a blog post.

09One person seen twice

M1 proved a guarantee about different people: thirty thousand requests, one seat, one winner. M2 is a guarantee about one person seen twice.

Alice books seat 14A. The database commits. The pod dies before the response leaves. Her browser shows a spinner, then an error. She clicks Book again.

Without M2, the second request runs from the top, finds no matching request_id, reads seats.status, sees booked, and returns seat_taken. Alice is told the seat is gone. She owns it. That is a direct violation of Guarantee 4, and once payment exists it becomes a double charge or a charge with no booking.

The client cannot know whether the lost attempt succeeded. Neither can the server after it restarts. You do not fix that by asking harder. You fix it by making a retry safe to repeat, so that whether or not the first attempt landed, running it again produces the same single outcome.

Decision 1 — the client mints the key

The client generates the idempotency key when the user clicks Book and sends it with the request. The server cannot generate it: if the server invents the key and the response is lost, the client never receives it, has nothing to send on the retry, and the server has no way to recognise the second request as the same intent. A key is only useful if it survives on the side that does the retrying.

The distinction that makes a stored “no” defensible

One request_id means one user intent, not one HTTP call. An automatic retry of the same click reuses the key — it is asking “what was my answer?”, not “book me a seat now.” If Alice clicks Book herself a second time, that is a new intent: the client mints a new key and gets a fresh answer against the current state of the world.

So the server is never claiming the seat is still taken. It is repeating the answer to a question already asked and already decided. Alice is never trapped, because asking again is always available to her.

Decision 2 — keys outlive the latest possible retry

The rule: the key must outlive the longest delay at which a retry can still arrive.

Why it matters, and it is not obvious. Alice loses the race and is told seat_taken. Four minutes later Bob's hold expires and 14A returns to free. Something retries her original request — a proxy, a mobile app resuming from a background queue.

  • Key row still exists → the server replies seat_taken again. Correct: same question, same answer.
  • Key row expired → the server has no memory of Alice. It runs the booking logic fresh, finds the seat free, and books it. She wakes up owning a seat she never asked for.

In practice the upper bound is unbounded — a phone in a tunnel can resend hours later — so no number is provably safe. The honest answer is a generous fixed window with a small accepted residual risk. Stripe keeps idempotency keys for 24 hours for exactly this reason.

Do not align the key lifetime with the hold timeout

With a 5-minute hold, seats start returning to free at the 5-minute mark. If the key also dies at 5 minutes, the server loses its memory at the exact instant the world starts changing. Both failure conditions line up by design rather than by bad luck. Sit well above the hold timeout, never on it.

Cleanup is a periodic background delete that never runs on the booking path — a user waiting on a seat must not pay for housekeeping:

DELETE FROM request_lookup WHERE created_at < now() - interval '24 hours';

Time-partitioning the table and dropping whole partitions is faster at scale, since dropping a partition is instant and a large DELETE is not. At roughly 30,000 rows per event that solves a problem this system does not have. Noted, not built.

10Claim-first, and why order is the mechanism

This is the hardest decision in M2 and the one a naive idempotency-key design gets wrong.

The failure a SELECT cannot catch

Alice's request gets stuck behind the connection pool and takes 3 seconds. Her client gives up at 2 seconds and retries with the same key. Requests A and B are now inside the database at the same moment, both carrying abc. Neither has finished, so neither has written anything.

If the key check is a SELECT, both run it and both find nothing. Reads cannot see uncommitted rows — that is not a bug, it is what isolation means — so B has no way to detect that A exists. Both proceed as first attempts.

A wins the CAS and commits. B's UPDATE matches nothing, so B loops, re-reads, sees booked, and returns seat_taken. One key, two responses racing back to one customer. She sees whichever arrives first. If seat_taken lands first, she believes she has no seat while owning one.

No ordering of SELECT and work helps, because the SELECT is blind to uncommitted siblings by definition. The check has to be something that collides with A, not something that reads around it.

The design

1. BEGIN
2. INSERT the key row (request_id UNIQUE)
     -> 23505: read the stored outcome and return it
3. run the CAS loop
4. UPDATE the key row with the final outcome, INSERT the booking row
5. COMMIT

When B tries to insert abc while A's uncommitted row sits there, Postgres cannot decide whether the constraint is violated. The answer depends on something that has not happened yet: if A commits, abc exists and B is a duplicate; if A rolls back, abc never existed and B is fine.

So Postgres does the only honest thing available. It makes B wait. B's INSERT blocks until A's transaction ends, one way or the other.

A's outcomeWhat happens to BCorrect?
CommittedB's insert fails 23505. B reads the now-visible key row and returns A's outcome. B never touches the seat.yes
Rolled backabc does not exist. B's insert succeeds and B does the real work. Alice gets one proper attempt instead of zero.yes

Both branches are correct and no coordination code was written. The uniqueness check does the waiting.

Why the order is the mechanism

If the claim is placed at the end, next to the booking insert, it never runs for the request that needs it. B loses the CAS, returns seat_taken at the status check, and exits long before reaching any insert. The constraint would be present in the code and unreachable in practice.

In CAS, any protection placed after the seat status read is dead code for losers.

B has to be stopped before it can form an opinion. Once B has read the status it already holds an answer, and it will return that answer. So the key insert is not a record of what happened — it is a claim on the right to decide, taken before any deciding starts.

Why both writes share one transaction

The key row and the booking row land together or not at all. If the booking rolled back while the key row survived, the key would claim a booking that does not exist, and every future retry would be handed the outcome of an attempt that never completed.

What it costs

Only requests carrying a request_id that another live request is already using ever wait. Two different customers fighting over seat 14A carry different keys, never collide in the key table, and meet only at the CAS UPDATE as before. CAS's property of never queueing on contention survives for real traffic.

The claim-insert does not reduce round trips — it fires on every request, and a write costs more than an indexed read, so per request it is slightly more expensive than the pre-lookup SELECT it replaces.

The sharpest line in M2

Cost is not the reason to do this. The SELECT design is wrong, not slow, and there was never a cheaper correct option to trade against. That is the difference from M1: there, three mechanisms were all correct and the numbers picked the winner. Here only one candidate is correct, so the numbers decide nothing.

11What may be memoized

OutcomeStoredWhy
bookedyesA decision was made
seat_takenyesA decision was made, and it can go stale — which is exactly why it must be pinned
sold_outyesSame shape as seat_taken; a freed hold could flip it
already_minenoIt is produced by a lookup hit — never an original decision
system_errornoNot an answer at all

Memoize decisions, never failures.

A system error is not a result, it is the absence of one. Nothing was decided, so there is nothing to repeat. Storing it would freeze a temporary failure into a permanent one — when a retry is precisely the correct response to a transient failure.

This is why request_lookup.outcome is nullable. Between the claim and the decision the row exists but nothing has been decided, so there is nothing honest to put in it. A null outcome means “claimed, still running.”

12The 1,000-pair overlap proof

TestBookSeatCAS_ConcurrentDuplicates fires 1,000 pairs of duplicate requests — 2,000 goroutines, same starting gun, 100 seats — where both members of a pair carry the same request_id and customer.

for p := range pairs {
    seatID := seats[rand.Intn(seatCount)]
    for i := 0; i < 2; i++ {
        go func(p int, i int) {
            <-start
            startTime := time.Now()
            out, _, _ := BookSeatCAS(ctx, pool, eventID, seatID,
                fmt.Sprintf("customer-%d", p), fmt.Sprintf("req-%d", p))
            results[p][i] = PairMatching{Outcome: out, startTime: startTime, endTime: time.Now()}
        }(p, i)
    }
}

Only two legal pair outcomes

  • One booked + one already_mine — the duplicate was recognised.
  • Both seat_taken — a different customer won the seat, and both halves agree.

Anything else fails the test, including the specific catastrophe M2 exists to prevent: one member returning booked while the other returns seat_taken.

The part that makes it a real proof

if r[0].startTime.Before(r[1].endTime) && r[1].startTime.Before(r[0].endTime) {
    overlapCount++
}
...
if overlapCount < (pairs / 2) {
    t.Errorf("only %d of %d pairs overlapped — the test cannot prove concurrency", overlapCount, pairs)
}

The test verifies that the two goroutines' execution windows actually overlapped in time, and fails if fewer than half did — so a pass proves a real race rather than a lucky serialisation.

This is the direct descendant of Lie 2 in the M1 harness. Having once shipped a benchmark that measured nothing because nothing raced, the next test was built to prove its own premise. That instinct — assert that the conditions you claim to be testing actually occurred — generalises to every concurrency test anyone will ever ask about.

The final assertion reconciles again: the count of booked/already_mine pairs must equal SELECT count(*) FROM bookings.

13Expiring holds (M4, in progress)

Real ticketing UX: a seat is held for ten minutes while the buyer checks out, then releases if not confirmed. This adds time as a failure dimension and opens a new family of races:

  • A hold expires at the exact moment the user clicks confirm.
  • The process dies between hold and confirm.
  • A background expiry reaper races a confirmation.
  • Held-but-never-confirmed seats leak inventory.

The hold acquisition, as written

UPDATE seats
   SET status = 'held',
       held_until = now() + interval '10 minutes',
       held_by = $1
 WHERE id = $2
   AND (status='free' OR (status='held' AND held_until < now()))
RETURNING held_until

Three things are happening in one statement, and they are worth naming separately:

  1. It is a compare-and-swap. Same shape as M1's mechanism 3 — the precondition lives in the WHERE, so check and act are one atomic operation.
  2. It absorbs expiry into the predicate. status='held' AND held_until < now() means an expired hold is automatically claimable by the next requester. No reaper is required for correctness.
  3. RETURNING makes the result self-reporting. A row back means the hold was granted and hands you the deadline in the same round trip; pgx.ErrNoRows means it was not. No second query is needed to find out whether you won.
Why now() and not a Go timestamp

Both the deadline and the comparison are evaluated by Postgres. If the application computed time.Now().Add(10*time.Minute) and sent it, correctness would depend on every replica's clock agreeing — which in M5 they will not. One clock, in one place, is the only version that survives multiple instances.

The retry path for holds

The 23505 branch reuses the claim-first pattern from M2, but has more to answer because a hold has states a booking does not. It joins the key table to the seat:

SELECT r.outcome, r.seat_id, s.held_by, s.status, s.held_until,
       s.held_until > now() AS still_live
  FROM request_lookup r
  JOIN seats s ON s.id = r.seat_id
 WHERE r.request_id = $1

still_live is computed by the database, in the same snapshot as the row it describes. Reading held_until into Go and comparing it against time.Now() would reintroduce exactly the clock problem the design just removed.

Other edges visible in the current code

  • No tx.Commit(ctx) exists in HoldSeat. There is defer tx.Rollback(ctx) and txc.Commit(ctx) for the savepoint, but the outer transaction is never committed on any path. Whatever the UPDATE wrote is discarded when the function returns.

15M5 and M6

M5 — multi-instance correctness

Run several instances of the service behind a real load balancer and re-test, do not assume. If the mechanism relies purely on the database as shared source of truth it likely extends — but “likely” is not the standard this project holds itself to, and the M1 proof gets re-run through the load balancer unchanged.

Where multi-instance bugs actually hide

In any in-memory optimisation added along the way. A per-process cache of seat status, a local rate limiter, an in-process hold timer: each is correct on one instance and wrong on three. The audit before M5 is simply list everything held in process memory — the list is the bug list.

M6 — load test, then designed overload

Two halves, and the second is the interesting one:

  1. Discover the ceiling. k6, a real flash-sale burst against the deployed system, p50/p95/p99, zero overselling under realistic load. Crucially: distinguish correctly rejected because actually sold out from incorrectly failed.
  2. Design what happens past it. Admission control (a bounded queue or semaphore), 429 + Retry-After, per-user rate limiting, and a measured goodput-under-overload curve showing graceful degradation instead of collapse.

A flash sale is organic DDoS, so backpressure is thematic here rather than polish. M6 is the ship line: milestone results written up, README leading with the crossover and the overload behaviour, deployed and reachable — then it stops being touched.

16Debts, drift and traps

Doc/code drift — worth reconciling

M2-design.md specifies a table named idempotency_keys carrying an event_id column. The migration that shipped is request_lookup, with no event_id. The behaviour is equivalent; the names are not. Either rename the table or amend the doc — a reader who greps for idempotency_keys today finds nothing.

Flagged, unverified — run it before quoting it

The shared harness's retry assertion requires booked → already_mine. Reading the source, BookSeatRowLock never inspects request_id at all: a retry of a successful booking locks the seat, finds the existing booking row, and returns seat_taken. That would fail the assertion. BookSeat (constraint) does look up request_id in bookings, so it passes.

If that is right, the retry check is only meaningful for two of the three mechanisms — which is defensible (M2 was scoped to CAS deliberately) but should be stated rather than left for a reader to discover. This is an inference from reading the code, not an observed test run. Verify it before repeating it.

Smaller traps worth knowing about

  • rand.Intn(rangeLow) panics if rangeLow is 0. With rangeLow = int(seatCount * 0.2), any seat pool below 5 makes it zero. The current array bottoms out at 10, so it never fires — a latent constraint on the test parameters rather than a bug.
  • Check 1 is a range, not an equality. counts[booked] is asserted between rangeLow and seatCount, because with many seats and a skewed target distribution not every seat gets attacked. The real oversell guarantee is carried by check 3b, not check 1. Say that clearly if asked — the loose bound looks like weak testing until the reason is given.
  • BookSeat returns already_mine without comparing the seat. Unlike the CAS path, it does not raise client_error when the same key arrives for a different seat.
  • The 6-second inter-batch sleep is inside the measured wall clock of the test but outside the per-request timings, which are what p99 is computed from. Fine as written; worth remembering before anyone tries to derive throughput from total runtime.

17Defending it out loud

Answer these from memory first, then check. The point is not to have read them — it is to have said them.

Why not just use SERIALIZABLE and let Postgres sort it out?

It would be correct, and it is a fair question to be asked. Under SERIALIZABLE, Postgres detects the conflict and aborts one transaction with a serialisation failure, which the application must then retry — so the retry loop does not disappear, it moves. You also pay predicate-locking overhead on every transaction, including the ones that were never going to conflict.

The deeper reason this project did not start there: the point was to understand what each mechanism costs a loser. SERIALIZABLE hides that behind the isolation level. It is the right production answer for a system with many varied conflicting transactions; it is the wrong teaching instrument for one hot row.

Why is READ COMMITTED not enough on its own?

Because atomicity is not isolation. Under READ COMMITTED each statement sees a fresh snapshot of committed data — which means two transactions can both read “seat is free,” both proceed, and both act. The read was accurate at the moment it happened and stale by the moment it was used. That gap between check and act is the entire bug class, and no isolation level below REPEATABLE READ closes it for you.

All three mechanisms are ways of closing that gap explicitly: the lock removes the concurrency, the constraint detects the collision after the fact, and CAS folds the check into the write so there is no gap to race in.

Your benchmark says CAS wins. Would you use CAS in production?

For a flash sale, yes — that is the concentrated regime and it is where CAS won. But the honest headline is “no single winner,” not “CAS is fastest,” and the claim is regime-specific. For a booking system where demand is spread across a large inventory, the row lock was measurably better, and its code is simpler and has no retry loop.

Also worth saying: the numbers were measured on one machine with the database in local Docker, at a fixed 80/20 skew. I would re-run them against the real deployment before betting a production decision on them.

What was actually hard about this?

Not the mechanisms — each is about thirty lines. It was learning not to trust my own benchmark. Three separate times the harness was measuring something other than what I thought: overlapping batches, goroutines released one at a time so nothing raced, and a single-seat contest that resolved in five milliseconds before enough competitors had even arrived.

Every one of those produced numbers that looked completely reasonable. The fix that stuck was building the next test so it proves its own premise — the duplicate-pair test asserts that the two goroutines' execution windows actually overlapped, and fails if fewer than half did.

Why claim the idempotency key first instead of looking it up?

Because a SELECT cannot see uncommitted rows. If the original request and its retry are in flight simultaneously, both lookups find nothing and both proceed as first attempts — and the customer can end up being told the seat is taken while owning it.

Inserting under a UNIQUE constraint collides instead of reading around the problem. The second insert blocks until the first transaction resolves, then either reads back the committed outcome or proceeds because the first rolled back. Both branches are correct and no coordination code was written.

And the order is the mechanism, not an implementation detail: in CAS, any protection placed after the seat status read is dead code for losers, because a loser has already formed an answer by then.

Why don't you store system_error in the key table?

Memoize decisions, never failures. A system error is the absence of a result, not a result — nothing was decided, so there is nothing to repeat. Storing it would freeze a transient failure into a permanent one, at exactly the moment when retrying is the correct response.

A stored seat_taken could be stale. Isn't replaying it lying to the user?

No, and this is the distinction the design rests on. One request_id is one user intent, not one HTTP call. A retry carrying the same key is asking “what was my answer?”, and the honest response is the answer that was given. The server is not claiming the seat is still taken.

If the user clicks Book again themselves, that is a new intent, the client mints a new key, and they get a fresh answer against the current state of the world. They are never trapped.

How do you know your concurrency test actually tested concurrency?

Because it checks. The duplicate-pair test records a start and end timestamp for each goroutine and counts how many pairs genuinely overlapped in time — a.start < b.end && b.start < a.end. If fewer than half the pairs overlapped, the test fails with “the test cannot prove concurrency,” even if every outcome was legal.

That check exists because an earlier version of the harness passed while nothing raced at all.

Why is expiry a predicate instead of a background job?

Because a background job is an extra thing that can be down, and an application timer dies with the process that holds it. Putting status='held' AND held_until < now() in the WHERE clause means an expired hold is claimable by the next requester automatically, with no reaper running and no clock outside the database.

A reaper is still worth having — it keeps availability reads honest and stops stale rows accumulating — but it becomes an optimisation rather than a correctness requirement. That distinction is the whole design.

What doesn't this project prove?

Multi-instance correctness — that is M5 and it is explicitly untested, because single-instance correctness does not automatically transfer. Behaviour past the capacity ceiling — that is M6. And the benchmark is an end-to-end request measurement on one machine, not an isolated measurement of contention: pool queueing, local Docker and system noise are all inside those numbers.

18Glossary

TermMeaning here
Check-then-actRead a value, decide from it, then write. The gap between the read and the write is where the race lives. The bug class this whole project is about.
Lost updateTwo transactions read the same value, both compute from it, both write. One update silently disappears.
Optimistic concurrencyAssume no conflict, detect it at write time, retry. CAS and the unique constraint are both optimistic.
Pessimistic concurrencyPrevent conflict by excluding others up front. SELECT … FOR UPDATE.
CASCompare-and-swap. The precondition lives in the WHERE clause, so check and act are one atomic statement. RowsAffected() is the verdict.
23505Postgres SQLSTATE for unique_violation. Distinguishes “someone beat me” from “the database is broken.”
SavepointA nested rollback point. In pgx, tx.Begin on an existing transaction. Lets an expected error be recovered from without poisoning the outer transaction.
Head-of-line blockingOne slow item at the front of a queue delays everything behind it. The row lock's failure mode under contention.
p99The latency the slowest 1% of requests exceed. The tail, where queueing shows up and averages hide it.
GoodputUseful work completed per second, as distinct from throughput, which counts work attempted. The metric that matters under overload.
Idempotency keyA client-minted id for one user intent. Repeating it must produce the same single outcome.
